# 提案: モバイル・折りたたみ端末に拡張可能な画面環境・適応レイアウト設計

Status: open (proposal; implementation not scheduled)
Updated: 2026-10-07
Related: [0004 Platform boundaries](0004-platform-rendering-and-native-boundaries.md), [0009 Browser backend](0009-browser-backend.md), [0011 Island migration](0011-electron-tauri-migration.md), [0018 MZed roadmap](0018-mzed-native-island-roadmap.md)

## 1. 目的・位置付け

**今すぐiOS／Androidの実装へ着手するのではなく、将来それらを追加するときに共通UIやアプリ状態を作り直さずに済むアーキテクチャを提案する。**

対象はiOS／iPadOS、Android、Web／ChromeOS、およびiPhone Duoを含む折りたたみ・複数表示領域を持つデバイス。特定機種の名前や画面サイズを共通APIの条件分岐に持ち込まない。

目指す差別化は「折りたたみ端末で描画できる」だけではなく、**開閉しても編集中の内容・選択・操作の文脈を失わず、同じアプリが表示領域を自然に使い分けられること**。アプリ作者が機種ごとにその仕組みを再実装しなくてよい状態を目指す。

本Issueは設計提案・レビュー用。着手時期、OS対応の優先順位、具体的な実装パケットは設計合意後に分ける。本Issueの追加は、バックエンド実装の開始、既存作業の優先順位変更、製品サポート宣言を意味しない。

## 2. 現状と拡張点

参照基準: `main` の `72d89475894e14f3fea9a3407e12a640da356ed9`（2026-10-07確認）。

- [アーキテクチャと依存境界](../../docs/architecture.md)には、共通の状態・レイアウト・sceneと、具体的なOSホストを分離する方針がある。この方向を維持する。
- [Backend](../../platform/backend.mbt)の`window_metrics`は幅・高さ・倍率の3値。折り目、遮蔽、複数の表示領域、動的な利用可能性を扱う共通の環境値を追加する余地がある。
- [イベント境界](../../platform/events.mbt)の順序付きpush/drainを活用し、環境変更と入力の対応を明確にする。
- [入力値](../../primitives/input.mbt)のマウス中心の表現を、将来のタッチ・複数接触・ペン・キャンセルを閉じない形へ拡張する。

全面的な書き直しや一括ディレクトリ移動は提案しない。以下の型名・パッケージ名は仮称であり、公開APIの確定ではない。

## 3. 責務・依存境界の提案

| 層 | 責務 | 境界 |
| --- | --- | --- |
| `core/` | App／Entity／文書・タスク状態 | OS名・機種名・GPU・折りたたみ判定に依存しない |
| `environment/`（追加候補） | 表示領域、分割・遮蔽、入力能力等のコピー可能な値 | 原則`primitives/`と標準ライブラリのみ。OSハンドルや具体的なホストを持たない |
| `adaptive/`（追加候補） | 環境とコンテンツの役割・制約から配置計画を決める | 決定論的な共通処理。OS APIを呼ばない |
| `layout/`・`element/` | 配置計画の実体化、サイズ計算、ヒットテスト、入力配信 | 機種別分岐を持たない。低層のlayoutからadaptiveへ逆依存しない |
| `scene/`・renderer | 配置済みの共通描画データと描画処理 | 折りたたみ時のUI方針をrendererへ持ち込まない |
| `platform/`・具体的ホスト | OSの事実を共通値へ正規化し、表示・入力・サービスを接続 | アプリ固有のペイン配置を決めない |

原則は**ホストが事実を報告し、共通の適応レイアウトが配置方針を決める**こと。環境値にウィンドウIDが必要なイベントは、platform側の外側のenvelopeにIDを持たせ、`environment -> platform`の逆依存を作らない。

パッケージを新設する場合は、既存の依存allowlistとアーキテクチャ文書へ明示的に追加する。公開APIを先に大量追加せず、最小の契約を実際の利用箇所で検証する。

## 4. ViewEnvironment: 画面環境の不変スナップショット

幅・高さだけではなく、当該ウィンドウ／埋め込みビューに実際に与えられた領域を表す。

| 情報 | 内容 |
| --- | --- |
| Viewport | 論理座標の表示範囲、倍率、必要な可視範囲・座標変換 |
| Regions / features | 分割境界、遮蔽領域、予約領域、利用可能な領域群 |
| Insets / occlusions | セーフエリア、システムUI、ソフトキーボードなど。単一の下端余白で表せない遮蔽も扱える余地を残す |
| Input capabilities | タッチ・マウス・ペン・ホバー・物理キーボードなどの能力と、取得できた情報 |
| Revision / observation | 環境リビジョン、情報の取得可否。入力・配置・描画との対応に使う |

### 不変条件

1. **分割と遮蔽を区別する。** 折り目による配置上の分割と、物理ヒンジ等による不可視領域を同一視しない。幅ゼロの分割境界も、描画不能な面積とは区別する。
2. **領域数を2に固定しない。** 領域・境界は上限を定義した可変長表現とし、単一領域を最小のケースとして扱う。複数領域を表現可能にすることと、多画面同時描画を実装済みとすることは別。
3. **端末全体ではなくビュー単位。** 折りたたみ端末の片側だけにアプリがある場合、無条件に2ペイン化しない。1ウィンドウ内の領域と、別ウィンドウ／別ディスプレイを混同しない。
4. **未取得・非対応・既知の空集合を区別する。** 情報がない場合は利用可能なviewportに基づく通常配置へフォールバックするが、観測していない「折り目なし」を報告しない。未知の障害物まで回避できるとは保証しない。
5. **座標と二重適用を防ぐ。** 論理座標、原点、倍率、viewportに適用済みのinsetを明文化する。OSが既に縮めた範囲からキーボード領域を二重に差し引かない。非有限値・範囲外・過大な領域数を検証する。
6. **環境を一貫した単位で更新する。** OSの複数コールバックを正規化したsnapshotを順序付きイベントとして受け入れる。新旧の倍率・領域・入力座標を無条件に混在させない。描画・ヒットテストは使用したrevisionを識別できるようにする。
7. **ヒンジ角度は必須入力にしない。** 配置に必要な領域情報と、演出・独自操作用の任意購読`HingeTelemetry`を分離する。高頻度なセンサ更新ごとの全体再レイアウトを前提にしない。

可視性・ライフサイクルと幾何環境を単一型へ集約するかは設計レビューで決める。ただし、その変更順序と状態遷移の契約は分離したまま曖昧にしない。

## 5. 役割付きペインによる適応レイアウト

アプリは「iPhoneなら左」「折りたたみなら2画面」ではなく、主コンテンツ・一覧・詳細・補助パネルの役割、最小サイズ、優先順位、同時表示できない場合の遷移方針を指定する。

| 利用可能な環境 | 標準方針の例 |
| --- | --- |
| 狭い1領域 | 選択中のコンテンツを表示し、一覧等はナビゲーションで切り替える |
| 広い1領域 | 最小サイズを満たす場合に一覧＋詳細を並べる |
| 左右に分かれる領域 | 境界をまたがず役割を割り当てる |
| 上下に分かれる領域 | アプリが許可した場合、上をコンテンツ・下を操作領域にする |
| 追加領域 | 優先度に応じて補助パネルを展開する |

標準方針は上書き可能とする。動画・図面・キャンバスを機械的に2ペイン化しない。全体幅だけでなく、各利用可能領域のサイズを判断に使う。

ペインのID・編集中の対象・ナビゲーション状態と、ペインの現在位置・表示数を分離する。同じ役割の再配置によって文書、選択、Undo履歴、スクロールの意味上の位置を作り直さない。標準レイアウトとカスタムレイアウトで同じ状態を使えるようにする。

## 6. 開閉・再接続時の継続性と入力契約

**アプリ状態、論理的な表示先、ネイティブビュー／ウィンドウ、GPUサーフェスの寿命を分ける。** サーフェスの喪失や外側／内側への表示切り替えを、文書の終了として扱わない。

1. 通常のリサイズ・開閉では共通モデルを保持して再配置する。ネイティブホスト再生成時は、論理状態を新しい表示先へ再接続できる境界を用意する。
2. プロセス終了からの復元は別の永続化契約とする。生のEntity・ネイティブポインター・GPU資源の保存を前提にしない。終了通知が必ず来ることにも依存しない。
3. 将来の入力値は接触ID、種別、開始／移動／終了／キャンセルを表せること。タッチを無条件にマウスイベントへ変換せず、共通のgesture層で意味のある操作へ変換する余地を残す。
4. 入力は表示先の世代と環境revisionへ束縛する。座標の解釈が継続できないドラッグは明示的にキャンセルし、古い座標で新しいボタンを起動しない。配置が変わってもtarget identityとcaptureの扱いを明示する。
5. 編集対象のIDと配置を分離する。キャレット、IME候補位置、selection、アクセシビリティの読み上げ順序・フォーカスを再配置と同期する。
6. ネイティブIMEセッションを維持できない場合は、確定・取消・再接続の方針を定義する。全OSでの無条件な変換中テキスト保持ではなく、黙った消失・二重確定・別対象への誤配送を起こさないことを要求する。
7. ソフトキーボード表示要求、システムの戻る操作、休止／復帰、メモリ圧力への接続点も将来のモバイル契約として扱う。マウス・物理キーボードの併用を排除しない。

## 7. 将来のホスト追加と互換性

### OSごとの接続方針

**iOS／iPadOS:** UIKitのビュー／シーン、表示領域・セーフエリア・取得可能な分割／予約領域を正規化する。iPhone Duo固有の詳細APIやSDK下限は、実装着手時の公式資料で確定し、共通APIへ漏らさない。

**Android:** WindowManager／`FoldingFeature`、Insets、Activity／Surface、入力サービスを接続する。AndroidX等が必要ならAndroidホストに限定し、既存のランタイム依存方針に対する例外と所有境界を文書化する。

**Web／ChromeOS:** 既存のブラウザ経路に接続し、Viewport Segments／Device Posture等は機能検出して利用する。APIの存在や同等性を全ブラウザで仮定しない。ChromeOSのWeb経路とLinux環境経由の動作確認は別に扱う。

**既存デスクトップ:** 通常の単一領域を初期値として通知し、同じ契約をリサイズ・倍率変更・入力機器の変化に活用する。

### 共通の設計要件

1. `supported`（実装能力）、`available now`（当該ビューでの現在の利用可能性）、権限・失敗を区別する。能力照会後でも操作の成否は実行結果で判断する。
2. 自前のウィンドウ／イベントループを所有するstandaloneホストと、外側アプリのビューへattachするembeddedホストの両方を表せること。coreへblockingなイベントループ所有を要求しない。現在のpush/drainを活用し、island型移行と整合させる。
3. FFIではコピーされた値、所有権、世代、解除完了を明確にし、OSハンドルを共通層へ露出させない。
4. Metal／GLES等の再利用は、実際に共通化できる描画責務に限定する。iOSをmacOSホストの別名、AndroidをUbuntuホストの別名にはしない。
5. 既存`window_metrics`やイベントとの段階的な共存・移行を定義する。公開enumへの追加やtraitの必須メソッド追加を、無条件な非破壊変更と扱わない。
6. 領域情報を必要もなく既存`SceneSnapshot`へ追加しない。まず適応レイアウト側で解決する。scene／ABIの意味や形式を変更する必要がある場合は、既存のversion・consumer検証規約に従う。

## 8. 段階的な進め方・非目標

| 段階 | 成果物 | 今回との関係 |
| --- | --- | --- |
| A. 設計 | 環境値、依存方向、状態遷移、フォールバック、互換移行をADR等へ記録 | この提案の合意対象 |
| B. 共通の検証用実装 | 単一領域の互換アダプターと、合成環境を注入するheadless／browserの検証 | 後続パケット |
| C. 適応コンポーネント | 役割付きペインを既存デモで検証。1領域・左右分割・上下分割と遷移を再現 | 後続パケット |
| D. モバイルホスト | iOS／Androidを共通契約へ接続し、各SDK・シミュレーター・実機で検証 | 別途優先順位を決める |
| E. 機種固有の体験 | ヒンジ操作・補助ディスプレイ・ペン等の任意機能 | 対応根拠のあるものから追加 |

初期段階では、未使用の巨大な抽象層、全OSの実装、共通のGPUライブラリ導入、一括リファクタリング、アプリ配布・ストア対応、Zed全体のモバイル移植を要求しない。upstreamへの変更も本Issueの範囲に含めない。

## 9. 設計提案としての完了条件

- [ ] 環境値の責務・依存方向・座標系・分割と遮蔽・取得不能の扱いがレビューされている。
- [ ] 1領域／複数領域、片側表示、埋め込みビュー、複数ウィンドウの意味の違いが記述されている。
- [ ] 開閉・再配置・サーフェス再接続・ホスト再生成・プロセス復元の責任境界が定義されている。
- [ ] 入力の世代／revision、gesture cancellation、IME、アクセシビリティの再配置規約が定義されている。
- [ ] 動的capabilityとstandalone／embeddedホストの接続方針が既存APIと整合している。
- [ ] 最小の導入手順、破壊的変更の扱い、非目標が合意されている。
- [ ] 後続実装は独立した受け入れ条件付きパケットへ分割する方針が記録されている。

**設計の完了は、モバイル／折りたたみ端末の製品サポート完了を意味しない。**

### 後続実装の検証計画（すべて未実行）

| 対象 | 受け入れ観点 |
| --- | --- |
| 純粋値・適応計算 | 同じ環境＋状態から同じ配置。1／2／3以上の領域、幅ゼロの境界、遮蔽あり／なし、入力値の上限・不正値 |
| 情報不足 | 未取得／非対応／既知の空集合を区別し、フォールバックがクラッシュや架空の能力報告を起こさない |
| 環境遷移 | 開閉、回転、キーボード表示、倍率変更、片側表示への移行が重なっても、古い座標の誤操作を起こさない |
| 状態・ライフサイクル | 選択、編集、Undo、スクロール、ナビゲーションの継続。サーフェス再接続とプロセス復元を別々に検証 |
| 入力・テキスト | 複数接触、ドラッグ中の開閉、capture解除、IME確定／取消、キャレット・候補位置、二重配送防止 |
| アクセシビリティ | 再配置後の読み上げ順序、フォーカス、非表示ペインの除外、操作可能な重要UIが遮蔽されないこと |
| 既存経路 | 既存のMoonBit target別check／testとホスト別smokeを回帰確認。実行した対象・コマンドとPASS／FAIL／未実行を記録 |
| OS別qualification | 合成環境、ブラウザのモバイル設定、シミュレーター、実機を区別し、OS／SDK／端末／backend／revisionを記録 |

`quickcheck`／`turtles.mbt`による不変条件・mutation検証、`hotpath.mbt`による再配置・割当の計測、`vlmkit`等による外部操作／視覚検証は、既存ツールの利用可能な機能・検証済み入力束縛に応じて適用する。ツール自体の追加機能や、未確認のモバイル操作能力を本Issueで対応済みとしない。
